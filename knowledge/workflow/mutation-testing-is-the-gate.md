統合フェーズの主関門は **オーケストレータ自身が回す変異テスト**。`integration-reviewer` ではない。

テストが通っただけでは何の証拠にもならない。**テストと実装を同じ worker が書いている**ので、
実装をなぞったテストでも通る。worktree を切って実装を故意に壊し、スイートが落ちるかを見る。

**実測（型階層 H1〜H3b）:**

| 作業 | 見つけた本物の欠陥 | コスト |
|---|---|---|
| integration-test-builder | 0 | Codex max 1 セッション |
| **変異テスト（自分）** | **1（唯一）** | スクリプト 2 本 |
| integration-reviewer（T1 時） | 実質 3 / 5。1 件は誤検知、並列テストの穴は見逃し | Codex max 1 セッション |

**効く場面:**

- `integration-reviewer` は**間違いが遠くまで伝播する所だけ**に絞る。他の unit が上に積む
  データ、スキーマ、出力が辺になる resolver。薄い CLI ラッパーには要らない
- `integration-test-builder` は残す。**永続するテストファイルを産む**から。ただしプロンプトは
  実装委譲と同じ規律で書く（契約を具体例で、スコープと非目標を明示、検証条件を指定）
- 生き残った変異は**必ず中身を読む**。等価変異（挙動が変わらない）はギャップではない。
  8 件中 2 件が等価だった
- 大規模コーパスの再計測は、**索引の中身が変わり得る unit だけ**。query / CLI の unit は
  既存の索引を使い回す

## 使い捨ての計測スクリプトを疑う

対象と同じ判断を自分で書き直すと、ほぼ必ず食い違う。そして**間違っているのはスクリプトの方**。
このセッションで 5 回連続そうだった。

| 報告しかけた内容 | 実際 |
|---|---|
| 「IBase の最大深さ 7」 | LIFO 探索で最短距離になっていなかった（正解 6） |
| 「HAPI 6,206 ファイル」 | `os.walk` が Maven の `target/` を歩いていた（5,103） |
| 「1,715 件の解決漏れ」 | スコープを無視して同名宣言の最後を拾っていた（欠陥 0） |
| 「同一行の宣言 49 件が誤り」 | 全部 `for` 文で宣言が先。実害 0 |
| 「41 件は位置を特定できず」 | 正規表現が `Iterator<String>` を扱えていなかっただけ |

**変異が no-op になっていないか、置換後の文字列を目で読む。**

「生存した変異」の正体が**自分の書いた変異が何も変えていないだけ**だった例が 2 回あった。

| 書いた変異 | 実際 |
|---|---|
| `"INSERT ..." if False else "INSERT ..."` | 両分岐が同じ文字列。何も変わらない |
| `results = results` | 代入しているだけ。切り詰めは消えていない |

アンカーが 1 箇所で見つかり、置換が成功し、テストが通ると、**「テストの穴」に見える。**
実際は変異が存在しない。生存を報告する前に、置換後のコードが本当に壊れているかを読む。
壊れていることを示す一番安い方法は、**その変異を入れた状態で対象を手で実行して出力が変わるのを見る**こと。

**手順:**

1. 食い違いを見つけたら、**報告する前に対象のコードを読む。** 3 件目は
   `type_unresolved` が `resolve_type` の戻り値をそのまま返すだけと分かれば、構造的に
   食い違いようがないと 1 分で判定できた
2. **判定不能が多い結果は使わない。** 49 件中 41 件が「不明」なのに残り 8 件から結論を出した。
   未分類が過半なら、それは計測ではない
3. **「該当する箇所の数」と「実害のある箇所の数」を混同しない。** 同一行に宣言があること自体は
   問題ではなく、呼び出しより後にあることが問題だった。条件を全部書いてから数える
